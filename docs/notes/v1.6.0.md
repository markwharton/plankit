version: v1.6.0
date: 2026-10-05
title: The first release covers everything
---

**No tag means nothing has been released.** The first `pk changelog`
covers the whole history from an implied `v0.0.0`, root commit included,
and says so first: `no release yet: the first release covers all N
commits`. Its entry links to the tag's commits, since a compare needs two
ends. To keep earlier history out of the first release, tag `v0.0.0` at
the last commit that is history; everything after it is the release. The
old hint to tag the newest commit is gone, and with it the way to mark
unreleased work as released by accident.

**Init places no tag, and works from any start.** `pk init` no longer
tags `v0.0.0`, so work committed before init is in the first release
like everything after it, and the order of init and first commits stops
mattering. When commits precede init's own, it says how many and names
the exact command that keeps them as history, `git tag v0.0.0 <sha>`.
`--no-baseline` is gone with the tag it skipped. A repository started on
`develop` runs `pk init --release main`, and `main` is created at the
root commit, carrying no unreleased work. `pk help init` has the recipe.

```
git init -b main
pk init
```

**Status reports the release branch as git shows it.** A policy naming
a release branch that does not exist gets the command that creates it at
the root. In merge flow, a release branch that has moved past its last
tag is noted with the number of commits not in a release. The tag line
now always prints, `none yet` before the first release.
