## 1. open: "a rejected tag update fails the fetch"

**git (run).** The clone's v1.0.0 points at a different commit from origin's, and origin also has v1.1.0 and v1.2.0:
```
$ git fetch origin --tags --quiet          → exit=1, no output at all
after: v1.0.0 kept as it was locally; v1.1.0, v1.2.0 created; refs/remotes/origin/main created
$ git fetch origin --tags
 ! [rejected] v1.0.0 -> v1.0.0  (would clobber existing tag)      exit=1
```
The fetch exits non-zero and still makes every other change, including the remote-tracking branches.

**Pages (read).** changelog SKILL.md:108-113: "pk changelog fetches origin's tags first and says so … Only when the fetch itself fails does it stop, with the error and the hint `git fetch --tags`." They say nothing about a rejected update.

**Code (read).**
- changelog.go:145 runs the fetch when `since.LatestTag == ""`. That means no version tag locally (`version.Latest`, semver.go:86-105), not no tags at all.
- changelog.go:151 is the fetch. When it fails, :158-161 asks `ls-remote`, refuses if origin has tags, and otherwise goes on.
- `TestNoLocalTagsAndFetchFails` (changelog_test.go:687) holds the refusal, but through a different cause.

**pk (run).** No version tag locally, and the clone's `notes` tag differs from origin's:
```
run 1: pk changelog --dry-run
  Error: no version tags found locally: git fetch failed: exit status 1
  Hint: origin has tags; fetch them: git fetch --tags                      exit=2
  tags after: notes, v0.0.0          ← v0.0.0 arrived anyway
run 2: pk changelog --dry-run  → Generating v0.1.0, exit=0
```

**Where they disagree:**
- **The design's reason.** pk.json's `fetch the tags` accepts "tags already has the member" because "The fetch runs only when the repository has no tags", and the fact `no local tags` says "the repository has no tags". The code fetches when there is no version tag, so a non-version tag can be there and clash. The reason is false against the code.
- **The message and hint.** The refusal gives no reason: `--quiet` swallows git's message. The hint's command fails the same way (exit 1, above).
- **What the refused run leaves.** It has already changed the tags, and the rerun passes because of that (this feeds Q10).

**Ways to settle.** All three below decide the open fact true, as git 2.54 behaves. In git.json, remove the fact and give `fetch tags` these handles:
```json
[ { "when": "origin does not answer", "then": "refuse" },
  { "when": "tags already has the member", "then": "fail",
    "says": "The update is rejected, the other tags are created, and git exits 1." },
  { "when": "tags is given a key twice", "then": "accept", "because": "A remote holds one tag of each name." } ]
```
Then pk.json's `fetch the tags` answers "tags already has the member" one of these ways:
- **A. `fail`:** `{ "when": "tags already has the member", "then": "fail" }`. This is what the code does: the tags arrive, then the run stops. Engine: Q1 gone, and Q10 now lists `fetch the tags` itself as a failure that leaves tags behind.
- **B. `refuse`:** `{ "when": "tags already has the member", "then": "refuse" }`. Engine: Q1 gone. But a `refuse` on a use says the run below changed nothing, which is not what git does.
- **C. Keep `accept`, with a true `because`.** Engine: Q1 gone. The code does not do this; it stops.
- Leaving pk's answer out raises a new unanswered question at `fetch the tags`.
- Deciding the fact false contradicts the 2.54 run.

Separately, to say what the code reads: `{ "name": "no local tags", "says": "the repository has no version tag" }`.
