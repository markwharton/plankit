title: The plugin runs wherever pk is
---

**The plugin works from any source once pk is on the PATH.** The
plugin's shim runs the binary bundled beside it, and when there is none,
because the plugin came from the GitHub repository, a directory listing,
or a checkout, it now runs the `pk` on the PATH instead. A `go install`
or Homebrew pk is enough for every hook to fire whichever way the plugin
files arrived. The marketplace archive is unchanged: its bundled binary
is still tried first.

```
go install github.com/markwharton/plankit/cmd/pk@latest
```

**The brief says when pk and the plugin disagree.** A pk from the PATH
can be a release behind the plugin's skills, or ahead of them. The shim
tells pk where the plugin is, and the brief's first sentence then names
both versions and the command that levels them, `go install` for pk or
`/plugin update plankit@plankit` for the plugin. Nothing reaches the
network for this: the plugin's version is read from its own manifest.
`pk help brief` has the sentence.

**Source builds report `dev` plus the commit again.** On Go 1.24 and
later a build from a checkout had started reporting the toolchain's
pseudo-version. `make build` and `make bin-local` now print `dev+<sha>`,
with `.dirty` for an uncommitted tree, as the version page says. Release
and `go install` builds are unaffected.
