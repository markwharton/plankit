title: plankit is a plugin
---

plankit is a Claude Code plugin. Install it once per machine and it
is present in every session; run `pk init` once in a repository and
it is on there. The repository gains one file, `.pk.json`, committed
with the code; `docs/plans/` appears when the first plan is
preserved. A behavior change arrives as a plugin update.

```
/plugin marketplace add https://plankit.com/marketplace.json
/plugin install plankit
```

`.pk.json` is the whole configuration. The pages for guard, preserve,
changelog, and release show what may go in their section of it: the
section's shape, each key's allowed values and default, and what a
wrong value does. The file's
first line names its JSON Schema, so an editor validates it as you
type; `pk status` reads it back and reports the first problem; and a
file that fails to load is reported by every hook rather than
silently ignored.

The plugin carries four hooks and the documentation. Guard runs
before every shell command the agent issues, protect before every
file edit, preserve when a plan is approved, and brief as a session
starts. Nothing is copied into `.claude/`; a repository set up by a
v0.x release removes what setup copied there, and `pk help overview`
lists the steps.

Every session in a plankit repository starts with a briefing. The
brief hook renders `.pk.json` as a few sentences of policy and
injects them as the session begins: the commit types, the
breaking-marker rule, which branches are protected, how plans are
kept. The text is derived from the file each time, so it cannot
disagree with what the other hooks enforce. `pk brief` at a terminal
prints what your sessions are told.

Guard asks before a breaking marker is committed. A `!` or a
`BREAKING CHANGE:` footer drives the next major version, and that
claim is the developer's to make. When the agent writes one, guard
answers with a question instead of a decision, and you confirm or
have it reworded. `guard.breaking` in `.pk.json` is the dial, `ask`
by default.

`pk ship` runs changelog then release as one command. Its only state
is the Release-Tag trailer, so a ship interrupted between the halves
resumes at release when you run it again. `/plankit:ship` in a
session dry-runs first and stops only on a major, for your go.

The documentation is one set of pages, written once. Claude Code
loads them as `/plankit:` shortcuts, `pk help` prints them in a
terminal, and plankit.com renders them. The `craft` page carries the
engineering standards and a prompt library. `/plankit:craft` loads
the standards; `/plankit:craft review` runs the review prompt.

pk works without Claude Code. Guard, changelog, release, ship, and
pin run in any terminal. `go install` builds it with Go, and the
release binaries for six platforms are attached to every GitHub
release, with `plankit.com/pk/<os>-<arch>` pointing at the latest.
