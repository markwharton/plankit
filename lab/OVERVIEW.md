# How the lab fits together

Read this first. `engine/DESIGN.md` is the reference for the design
language, and `README.md` is the reference for the lab's page; this
page says what the pieces are and how they work together.

## The idea

Before code is written, say what a system should do, precisely enough
that a machine can try every case and point at what is missing. Then
hold the code to it. Errors are found in the definition, not after the
code ships: Hamilton's "development before the fact".

## The pieces

| Piece | What it is | Written |
|---|---|---|
| A design | What one system should do: what it reads and changes, what can be wrong, and what it does about each. `engine/pk.design` is pk's. | Once per system, by the owner or by a model the owner checks |
| The engine | A program that plays any design: every combination of facts, to its end. It reports each place the design is silent or contradicts itself. `engine/engine.py`. | Once, for every design |
| The parser | Reads a design written as text, and prints one. `syntax/`, with its lexer generated by Ragel. A design can also be written in JSON. | Once, for every design |
| A description of code | A second design, saying what the code does now, written by reading the code. The engine plays it beside the design and reports each difference. `engine/pk-code.design`. | Once per system, again when its code changes |
| A blind round | A fresh session writes a design from a system's pages alone. Where it has to guess, the pages are silent. `engine/BLIND-TEST.md`. | When the pages or the language change |
| The lab | A web page to edit a design and see what the engine finds, drawn five ways. `lab.py`. | Once |
| The code | The system itself, written by hand, test first, to do what the design says. | Per system, as always |

The engine, the parser and the lab are general: nothing in them is
about pk, and a new system needs only its design. They change only
when the language does, and every design gains when they do.

## A walk through pk

1. **The design.** `pk.design` says what `pk changelog`, `pk release`
   and `pk ship` should do, standing on `git.design`, a design of the
   git operations pk runs.
2. **Playing it.** The engine plays 635 plays and asks no questions:
   every fault has an answer, and every change says what happens to it
   after a failure.
3. **A finding.** A blind round's design had a preRelease hook that
   commits. The engine reported the hook's commit left behind when the
   release failed.
4. **Confirming it.** A run in scratch repositories showed it was real,
   and worse: in merge flow the next release could not run at all.
5. **The fix.** Go code, written test first. It shipped in v1.10.4.
6. **Holding the code to the design.** `pk-code.design` was described
   again from the new code. Played against `pk.design` with
   `--against`, the difference was gone.

The six fixes this work added to v1.10.4 were all found this way: by
the engine's questions on the design, by blind rounds, or by the
code's description played against the design.

## Out of control, and under control

A system is out of control when its cases exist but nobody has listed
them: the bugs are there, and nothing shows where. It is under control
when every case is listed, has a decided outcome, and a machine checks
each one. What is left over is a named list that can be measured.

Code review checks the code against the cases the reviewer thinks of.
None of the bugs this work found in pk was a wrong line; each was a
case nobody had thought of:

| The bug | Where it was | What made it visible |
|---|---|---|
| A preRelease commit stopped the next release | Between two runs, in merge flow only | Every run starts from what earlier runs left, and every change says what happens after a failure |
| A dry run wrote refs | A promise ("writes nothing") against a `git fetch` | The expectation that a dry run changes no lasting place, checked in every play |
| A pre-release tag counted as a release | A kind of value nobody pictured | A fact for a tag that is not a release version, which every step that reads tags answers |
| A broken trailer got a second release commit on top | A state an earlier run left | The same: a run reads what earlier runs left |
| A first release made without a word | A failure between two calls to origin | Every call to origin is a fault each step answers |
| The ship page's "as it was before" | The page against what the code keeps | The design is written from the pages, so their words are tested too |

How much of a system is under control is measured by what can be seen
now that could not be seen before:
- **Bugs found that review did not find.** Six in pk, and two pages
  that said the wrong thing.
- **Cases with a decided outcome.** All 635 of pk's plays.
- **Decisions on record, with their reasons.** Such as "a dry run
  writes nothing" and "ship resumes a release already pending".
- **The gaps, as numbers that shrink.** The differences between the
  code and the design, 25 now, and the statements no test holds, 36 of
  66 now.

## What it finds, and what still needs code

Without writing the system's code, it finds:
- what the pages leave unsaid, or say two ways;
- what a decision means in every combination of facts;
- where the code does something the design does not, once the code is
  described;
- which statements of the design no test holds.

It does not write or run the system's code. Fixing is still code. The
design says what to change and which test should hold it, a run
against the real system confirms a finding before the fix, and
`--against` shows when the code agrees.

## Two checkers

The lab opens two kinds of definition, and they come from two
checkers:
- **`control/`**: the first checker, in Go. It checks a definition
  file and its descriptions in its own JSON format: the contacts
  examples, and `definition/pk.json`. The standard it serves is
  `docs/control.md`. In the lab, its controls read "Path" and "Break".
- **`engine/`**: the newer engine, in Python. It plays a design you
  can run, written as text or in JSON. In the lab, its controls read
  "Given" and "Wrong".

Which of the two stays is not decided: either the engine replaces the
checker, or it takes on what the checker has that it lacks.

## Where it is going

The aim is that a model working on a system has a checker that guides
its work, and cannot change what judges it:
- the model writes the design, and the code;
- the owner decides the design;
- the engine judges the work, and no model writes it as part of the
  work it judges;
- plankit's guard keeps the decided design and its acceptances out of
  the worker's reach.

It comes into plankit in stages: the language page as a skill, then
the engine as a `pk` command in Go, then the lab. The first real run
is plankit's own next change: design it, have one session build it,
have another describe the code cold, and settle each difference. See
`engine/DESIGN.md`, "Who does what" and "Its home".
